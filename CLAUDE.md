# Системные правила

## Экономия токенов в больших проектах

Эти правила применяются ВСЕГДА, но особенно строго — когда задача выглядит крупной (рефакторинг секции, создание нового документа/презентации, серия правок по >2 файлам, любое «переделай весь блок X»).

### Триггеры «дорогой задачи»

Прежде чем начать работу, оцени запрос. Признаки того, что задача потребует много токенов:
- Затрагивает несколько файлов или несколько секций
- Просьба «переделать», «переписать», «реструктурировать», «собрать с нуля»
- Создание документа > 200 строк (КП, презентация, шаблон)
- Большой рефакторинг визуала или логики
- Неоднозначная формулировка («сделай как-нибудь покрасивее», «оптимизируй»)

При срабатывании триггера → действуй по правилам ниже.

### Правила работы с инструментами

1. **Edit > Write для существующих файлов.** Edit передаёт только diff. Write переотправляет весь файл целиком — используй только при создании нового файла или полной перезаписи.

2. **Не перечитывай файл после успешного Edit.** Edit детерминирован: ответ «успех» = текст ровно такой, как ты задал. Re-read = двойной расход без выгоды.

3. **Grep с context (`-A`/`-B`/`-C`) вместо Read больших кусков.** Когда нужны 3–10 строк рядом с матчем — Grep дешевле, чем читать 50 строк через Read.

4. **Один большой Edit > пять мелких.** Если правишь несколько связанных мест в одной структуре — заменяй блок целиком одним вызовом Edit. Каждый отдельный Edit — это round-trip.

5. **Параллельные tool calls в одном сообщении.** Когда правки независимы (разные файлы, разные блоки) — отправляй несколько Edit/Read одним сообщением.

6. **Делегируй большое в Agent.** Если нужно «прошерсти весь репо», «поправь все вхождения X», «сгенерируй длинный текст с нуля» — запускай Agent (subagent_type=general-purpose). Он работает в своём контексте и возвращает только итог. Основная сессия не пухнет.

7. **Не ставь TodoWrite для тривиальных задач.** Только для реально многошаговых работ (3+ независимых шага). Иначе TodoWrite сам становится накладным расходом.

### Правила ответов

8. **Не пересказывай в ответе то, что уже видно в diff.** Не делай таблиц «было/стало» по тривиальным правкам. Достаточно: «изменил X в Y», без раздува.

9. **Не делай длинных Markdown-сводок в конце каждого ответа.** Используй заголовки и таблицы только когда они реально упрощают чтение, а не «для солидности».

10. **Если пользователь начинает запрос словом «коротко» (или просит коротко в любой форме) — отвечай без развёрнутых пояснений.** Только результат и одно предложение про суть.

11. **Не благодари, не извиняйся, не делай разогрева.** Сразу к делу.

### Правила работы с пользователем

12. **AskUserQuestion на любой развилке — обязательно при крупной задаче.** Не угадывай. На каждое неоднозначное место в большой задаче — вопрос с 2–4 вариантами ответа в кликабельной форме. Лучше задать 2–3 вопроса заранее и сделать сразу правильно, чем сделать наугад и переделывать.

13. **Структура хороших AskUserQuestion-вариантов:**
    - 2–4 опции (не больше)
    - Первая — Recommended, если у тебя есть обоснованное мнение
    - Каждая опция содержит `description` с конкретными последствиями выбора (что именно произойдёт)
    - Вопросы должны закрывать самые «дорогие» развилки (где переделывать потом будет дороже всего)

14. **Перед стартом крупной задачи — короткий план через AskUserQuestion ИЛИ открытым текстом.** Сформулируй: что я понял из запроса, какие есть варианты, какой предлагаю. Подтверждение клиентом займёт 1 клик и сэкономит сотни токенов на переделках.

15. **Не задавай вопросы по тривиальным мелочам.** Если стоимость ответа меньше стоимости переделки — действуй сам. AskUserQuestion — для ключевых развилок, не для «какой цвет фона».

### Управление сессией

16. **Предлагай открыть новую сессию, когда:**
    - Текущая длится долго и накопила много истории
    - Запускается принципиально новая задача (новый документ, не связанный с текущим контекстом)
    - Пользователь упоминает, что «контекст уже большой»

17. **Между фазами работы используй `mcp__ccd_session__mark_chapter`** — это даёт явный сигнал «эта тема закрыта», и не нужно тащить её детали вперёд.

18. **После серии правок предлагай коммит через GitHub Desktop.** После коммита история становится «чужой памятью» (git log) — можно начинать новую сессию без потерь.

### Краткое резюме

Перед тем как взяться за крупную задачу, спроси себя:
- Можно ли это делегировать в Agent? → делегируй
- Есть ли неоднозначности? → AskUserQuestion с 2–4 вариантами
- Можно ли свести к одному большому Edit? → своди
- Нужно ли пересказывать результат? → нет, если diff говорит сам за себя

Цель — максимум полезной работы за минимум токенов, без потери качества.

## Терминология голосового ввода

- "код код", "код", "кода", "клоуда" — скорее всего имеется в виду **Claude Code**
- "антигравити" — **Antigravity** (agent-first IDE от Google)

Глаголы в 1-м лице — команды во 2-м лице:
- "сделаю" → "сделай", "приступаю" → "приступай", "посмотрю" → "посмотри", "проверю" → "проверь"

## Plan → Do → Verify

Любая задача = три шага. Не пропускай.

**1. ПЛАН** — перед тем как делать:
- Разберись в задаче (читай код, контекст)
- Определи критерии проверки: как убедишься что сделано правильно?
- Крупная задача → уточняющие вопросы + план пользователю

**2. ВЫПОЛНЕНИЕ** — делай по плану:
- Следуй плану, не уходи в сторону
- Проблема в процессе → вернись к шагу 1

**3. ПРОВЕРКА** — перед тем как сказать "готово":
- Проверь по критериям из шага 1
- Перечисли что проверил: `"Проверил: X ✓, Y ✓, Z ✓"`
- Нет проверки = не готово

**Фейл проверки:** диагноз → скорректируй план → повтори. Макс 3 итерации, потом — к пользователю.

**Масштаб:** крупная → полный PEV + план пользователю; средняя → план в голове, проверка обязательна; мелкая → только проверка.

## Правила поведения

**НЕ ВЫДУМЫВАЙ** — если чего-то не знаешь, скажи прямо. Никогда не додумывай факты и детали.

**Уточняющие вопросы** — перед важными/крупными действиями (архитектура, деплой, удаление, рефакторинг) — задавай от 5 до 20 уточняющих вопросов, прежде чем приступать.

**Проверки по типу файла:**
- Изменил `.py` → `python3 -m py_compile файл.py`
- Изменил `.yaml` → `python3 -c "import yaml; yaml.safe_load(open('файл'))"`
- Изменил `.json` → `python3 -c "import json; json.load(open('файл'))"`
- Написал текст → перечитай на AI-маркеры, факты, стиль

**Plan Mode:**
1. После составления плана: "План составлен. Перечитай, если хочешь что-то изменить — скажи. Не приступаю к коду, пока не одобришь."
2. Изменения — через план, не через код. Обнови план → покажи → одобрение → правь код.
3. Сохраняй план в `tmp/plans/` проекта.

**Правила для кода:** python3 (не python), pip для зависимостей, скачивания в `~/Downloads/`, схемы — ASCII art.

## Разработка лендинга

При создании лендинга с нуля или редактировании существующего — всегда применять скилы в этом порядке:

1. `design-taste-frontend` — основа: нешаблонный лейаут, реальная дизайн-система
2. `high-end-visual-design` — шрифты, тени, карточки уровня дорогого агентства
3. `gpt-taste` — GSAP ScrollTriggers, editorial типографика, bento-сетки
4. `emil-design-eng` — UI-полировка, микроанимации, детали которые делают интерфейс живым
5. `hallmark` — убрать AI-slop паттерны (шаблонные тени, градиенты, формулировки)
6. `refactoring-ui` — финальный аудит: визуальная иерархия, спейсинги, цвет

**Дополнительно по ситуации:**
- `imagegen-frontend-web` — если нужна генерация дизайн-референсов по секциям
- `image-to-code` — если есть скриншот/макет для воспроизведения
- `scroll-world` — если нужен скролл-синематик (камера летит через мир)
- `brandkit` — если нужна айдентика с нуля (логотип, палитра, гайдлайн)
- `stop-slop` — финальная очистка перед сдачей

## Анимации и motion

При добавлении анимаций, переходов, микроанимаций или работе с motion:

1. `animate` — строит анимацию с нуля: нужна ли она, цель, кривая, длительность, прерывание
2. `emil-design-eng` — философия UI-полировки, когда и как анимировать детали
3. `apple-design` — плавные физические анимации, gesture-driven UI, spring-переходы
4. `improve-animations` — аудит существующих анимаций в кодовой базе (read-only, план)
5. `find-animation-opportunities` — найти места где анимация нужна, но её нет

## UI компоненты и полировка

При создании или улучшении UI-компонентов:

1. `emil-design-eng` — невидимые детали, которые делают интерфейс живым
2. `refactoring-ui` — визуальная иерархия, спейсинги, цвет, глубина
3. `break-ui` — стресс-тест компонента на крайние случаи (длинные имена, пустые данные, emoji)
4. `hallmark` — убрать шаблонные AI-паттерны

## Мобильная адаптация

При адаптации под мобайл или разработке мобильного интерфейса:

1. `mobile-native` — CSS и meta-фиксы чтобы сайт ощущался нативным на телефоне
2. `animate-expo` — анимации в React Native / Expo (Reanimated, Gesture Handler)
3. `apple-design` — iOS-паттерны: шторки, свайпы, momentum-скролл
